# campaign-service

Campaign CRUD and orchestration for MCP Factory: lifecycle, budget tracking, run coordination.

## CRITICAL: read-only by default

When the user shares logs, errors or bug reports: ONLY diagnose and explain. NEVER write code, branch or open PRs unless explicitly asked to implement a fix (the same logs often go to several agents in parallel for analysis). Before ANY structural change (endpoints, DAG nodes, services, schema, workflows): stop and ask. The root cause may be in another service.

## THE OWNER RULES (override everything below)

A campaign's STATUS is the CUSTOMER's statement of intent; nothing else changes it. FUNDING and RUNNING are different acts (2026-09-06: conflating them left 5 brands with duplicate live campaigns and resurrected deliberately stopped ones, ~$37 to 4 customers).

1. **MONEY NEVER STARTS ANYTHING.** A funded ceiling provisions no campaign. Deleted: `ensureFundedFunnelCampaigns`, `fundedPairs`, `provisionFundedPairsForQuietBrands`, `funnelCampaignName`, the "resume a funded stopped row" branch, `brand-sales-funnels-client.ts`, `feature-sales-funnels-client.ts`, `feature-workflow-client.ts`, the `funded*` helpers on the budget client. Billing is read for two things only: is an EXISTING campaign funded (the hold), and which ceiling paces it. "Why isn't it running" = "nobody launched it".
2. **A CAMPAIGN THAT EXISTS IS NEVER CREATED AGAIN.** `POST /campaigns` matches the identity's incumbent WHATEVER ITS STATUS (live first, then latest stopped) and hands it back STARTED (it is only ever a person's act). The unique index is partial on `ongoing`; prod has 663 stopped rows sharing 33 identities, history is never rewritten, so the guard lives in the LOOKUP.
3. **A SYSTEM CONDITION NEVER CHANGES A STATUS** (one exception below). Out of credit, audience exhausted, budget spent, `maxBudgetTotalUsd`, `maxLeads`: each blocks the RUN only; it runs again on a later tick. `autoStopCampaign`/`autoStopped` are gone from gate-check; `/end-run` exhaustion marks the audience and reschedules on `NO_SERVEABLE_AUDIENCE_RECHECK_MS`. Nothing RESUMES anything: `campaign-resume.ts`/`isResumableStopReason` are deleted. `STOP_REASONS` = `manual`, `org_teardown` (a person writes) + `payment_declined`, `no_payment_method`. `audience_exhausted`/`max_leads_reached` are RETIRED.
4. **A FUNDED CEILING NAMING NO LEG IS A LOUD NAMED ERROR.** Never defaulted to a coarser figure, never skipped silently: `legKeylessFundedCeilings` + `reportLegKeylessCeilings` `console.error` org/brand/funnel/channel/offer/cents/grain, deduped per identity on the 10-min cadence. It does NOT hold the brand.

Unchanged: the funding HOLD (unfunded waits on `FUNDING_RECHECK_MS`), ceiling precedence, turn planner and cohorts, fail-CLOSED on an unreadable ceiling, onboarding launch (creates AND starts), `PATCH /campaigns/:id status=activate|stop`, offer attribution adoption.

### The one exception: `payment_declined` / `no_payment_method` (owner, 2026-09-26/27)

An org whose card billing cannot charge stops every campaign.
- **Billing states the verdict**: `lib/payment-hold.ts` reads `GET /internal/accounts/by-org/:orgId/payment-outlook`; `state === "charge_blocked"` ⟺ held, `blockedReason` carried verbatim. 404 = not held. `blockedReason: no_chargeable_card` maps to stop reason/refusal `no_payment_method` (nothing was declined); every other reason is `payment_declined`.
- **Sweep** (`lib/payment-hold-sweep.ts`): first thing every tick, own `PAYMENT_HOLD_RECHECK_MS` (10 min). Stops all ongoing campaigns of a held org (`stopOrgCampaignsWithHistory`, source `payment_hold`); a campaign already stopped keeps its reason. Fail-SOFT.
- **Every start path refuses a held org** (`POST /campaigns`, `POST /campaigns/start-funded-pair`, `PATCH status=activate`) with **409** `{error, reason, blockedReason}` (`error` is customer-facing English the dashboard renders verbatim), whatever stopped the campaign. Billing unreadable = **502** `billing_unavailable`.
- **NOTHING RESUMES AUTOMATICALLY**: the customer presses start once billing stops saying `charge_blocked`. Owner accepted; auto-resume would be the retired resume sweep.
- `tests/setup.ts` mocks `lib/payment-hold.js` to "not held"; `tests/unit/payment-hold.test.ts` uses `vi.importActual`.

## Sales family, channels, refusals

- **`SALES_FAMILY_FEATURE_SLUGS` membership is a MONEY statement**: "this campaign's ceiling is billing's per (offer, leg, channel), read live every plan". `isSalesFamilyFeature` drives gate-check's `isSalesFeature`, the `maxBudget*` refusal, create-time offer/leg requirement, turn planner, `spendable-budget`. Members: cold email channels, `google-ads`, `ai-meeting-booking`, `pr-expert-quote-outreach`. Adding a channel = one line there + its `CHANNEL_BY_FEATURE` token; no column/table/branch.
- **Never widen the family by catalogue** (read synchronously on gate-check's money path and in SQL; an unreadable catalogue must not flip whether a budget column binds). A PLATFORM-operated funded channel the family does not name is not provisioned and warns "campaign-service does not pace it" (fail-CLOSED, visible). Add a channel only when workflow-service has a dynasty for it (google-ads has none: do not add; pr-expert-quote-outreach has 8, `ai-meeting-booking` has its own). Tokens never change when a channel changes family; retired `pr-expert-quote-opportunities` is never added.
- **`OUTBOUND_SALES_FEATURE_SLUGS`** (cold-email channels only) is the narrower "shares the brand's LEADS and SENDING ACCOUNTS" question; exactly these asks use it: the serialization cohort, greedy workflow rotation (prices send-tagged outcome evidence), the extend-audience lifecycle email, and the legacy per-campaign `daily_budget_cents` mirror written by `PATCH /brands/:brandId/daily-budget`. google-ads, ai-meeting-booking and pr-expert-quote-outreach are NOT in it.
- **A channel the CUSTOMER operates gets a campaign with NO workflow**: `campaigns.workflow_slug` is nullable (migration 0054), NULL = no DAG. WHO operates is features-service's statement (`GET /public/channels` → `channels[].operatedBy`, read by `src/lib/channel-operator-client.ts`, the ONE reader). Unknown slug or unreadable catalogue answer "platform" (today's behaviour; never stand up a workflow-less campaign on a guess; warns). Create/update API still REQUIRES a slug; only provisioning writes NULL. Never scheduled/triggered/spending: `workflow_slug IS NOT NULL` on the due-campaign claim, `claimStuckCampaigns` and the cadence snapshot; `/start-run` 400s; activation triggers nothing.
- **`maxBudget*` is REFUSED for the family** (`salesMaxBudgetRefusal`, `src/lib/sales-outreach-campaign.ts`): `POST`/`PATCH` 400 a sales-family campaign that STATES one (update tests the feature the update leaves it on). Non-sales features still pace on those columns (never drop them; `gate-check`'s `!isSalesFeature` branch stays). Migration 0053 nulled legacy values for the 3 slugs of its day (audit: `campaign_max_budget_decisions`); it is frozen SQL, a channel joining later is never retro-nulled. `daily_budget_cents` is the funding mirror, untouched.
- **Which funnel/leg a channel may sell or perform is features-service's statement**, read from the public catalogue and joined VERBATIM against `campaigns.leg_key`; never parse a leg identifier, never hold a leg matrix.
- **Offer**: `campaigns.offer_id` (migration 0050) is brand-service's UUID, carried never derived, optional on create, part of the identity key (`coalesce(offer_id,'')`, migration 0056), decides no money question. An offer belongs to the (org, brand) pair: `makeOfferResolver`/`brand-offers-client.ts` name `x-org-id` (load-bearing). Backfill is a re-runnable script (`scripts/backfill-campaign-offer.ts`, dry-run default, `--apply`), never a migration; it writes only exactly-one-offer pairs and never guesses multi-brand campaigns. Live offer-less campaigns are ADOPTED on the tick by `adoptOfferForPairSafely` (`src/lib/campaign-offer-adoption.ts`): exactly one offer on the pair or nothing written, asked at most once per `OFFER_ADOPTION_RECHECK_MS` (10 min), no read when nothing is missing, zero/several offers SAID only when a LIVE campaign is affected, a stopped row is written when its pair resolves (only `offer_id` moves), idempotent, fail-SOFT.
- **Audience subset** `campaigns.audience_ids` is a HARD filter on the audience bandit (`requiredAudienceIds`, no fallback); NULL/empty inherits the brand's active audiences. Distinct from singular `audienceId` (attribution).

## `POST /campaigns/start-funded-pair` (a person's act)

Only ever runs because somebody pressed a button; `tests/unit/no-legacy.test.ts` asserts `lib/startable-pair.ts` is imported only by `routes/campaigns.ts` (a scheduler importing it is the deleted question returning).
- Caller states brand, offer, LEG, channel (offer+leg REQUIRED, else `leg_required`). Workflow (re-picked each run), name (derived) and money (billing's) are NOT the caller's: body is `.strict()`.
- Refusal `reason` codes: 400 `leg_required`, `channel_not_paced_here`, `unknown_channel`, `leg_not_performed`; 409 `not_funded`, `no_workflow`; 502 `catalogue_unavailable`, `billing_unavailable`, `workflow_unavailable`. `error` is customer-facing English. "Nothing can run this channel" and "could not read what runs it" stay different answers.
- A pair with a campaign never gets a second: live is returned untouched (`started: false`), stopped is STARTED via `setCampaignStatus` source `start_funded_pair`; an incumbent missing offer/leg is ADOPTED (filled, never overwritten). Otherwise an ordinary sales-family campaign (same ceiling, hold, planner, cohorts); a customer-operated channel gets no workflow and `NULL next_run_at`.
- **Probing `POST /campaigns` against a real org is a WRITE**: it matches the incumbent and RESTARTS it, overwriting `workflow_slug` and stamping `maxBudget*`. Verify refusals (4xx writes nothing) freely; take controls from the DB or use a non-existent org/brand. Recovery: read prior values from evidence (campaign NAME carries the dynasty; `runs` confirms), restore, stop THROUGH the API, confirm zero runs/spend in the window.

## Predecessor, answerer, step trigger, idle runs

- **`GET /internal/campaigns/:campaignId/predecessor`** (`src/lib/predecessor-campaign.ts`): a lookup over held state, nothing stored. The predecessor is the leg whose catalogue `toStep` is this campaign's `fromStep`, on (org, brand, offer, leg). Never guessed: `predecessor: null` with `absence: entry_leg` (entry leg), or no leg/offer/brand/none bought. Distinct answers: unreadable catalogue **502**; leg no longer published **409**; two LIVE siblings on the preceding leg **409**. Live row wins, else latest stopped.
- **`GET /internal/campaigns/:id/answerer` + `POST /internal/campaigns/answerers`** (`src/lib/answering-campaign.ts`): who answers the people a campaign holds, judged by the claim path's OWN `resolvePredecessorCampaign`. Nobody is always named: `no_answering_campaign` (+ `startableFeatureSlugs`), `answering_campaign_stopped`, `answering_campaign_serves_another`, `no_leg_continues`, `campaign_states_no_leg|offer|brand`; unreadable = 502. Starts/provisions nothing (the customer sees it in lead-service and chooses).
- **`POST /internal/campaigns/trigger-for-step`** (`src/lib/step-trigger.ts`): a lead reaching a STEP runs the campaign bought for the leg OUT of it NOW. Leg asked from the catalogue, never derived/parsed; join on (org, brand, offer, leg). Same dispatch as the scheduler (`ensureCampaignRunId`, greedy pick, `/execute`), so the run starts at `gate-check`; same guards (one run per campaign, one per brand COHORT, shared `campaignFunding` fail-CLOSED). Bad scope fails loud (unpublished step 400, unreadable catalogue 502); everything else is 200 with a NAMED skip (`no_workflow`, `unfunded`, `global_sales_budget_reached`, `run_in_flight`, `cohort_run_in_flight`, `incomplete_campaign`, `dispatch_refused`) or empty. Offer matched exactly. Time-based path byte-identical.
- **`noWorkAvailable`** on the `/end-run` body (optional; absent = work was done): the DAG says a run had nothing to do, and ONLY the reschedule delay changes to `NO_WORK_RECHECK_MS` (10 min, `src/lib/idle-run.ts`). It never stops, never marks exhaustion, kept as a separate constant from `NO_SERVEABLE_AUDIENCE_RECHECK_MS`. A FAILED run's claim is ignored (the failure backoff wins). Idle backstop only: a real event goes through trigger-for-step. (Cost: one idle campaign was 52% of the fleet's run ledger.) The workflow-service DAG must send it; until then behaviour is unchanged.
- **`stopCampaign=true` on `/end-run` is AUDIENCE-scoped and stops NOTHING**: marks `req.audienceId` exhausted in `campaign_audience_exhaustion` (24h TTL via `getFreshExhaustedAudienceIds`, excluded by the bandit; no audience id = nothing marked), reschedules on `NO_SERVEABLE_AUDIENCE_RECHECK_MS` whenever `hasServeableAudience` finds nobody, and sends the extend-audience email ONLY if the campaign ever exhausted an audience (`hasExhaustedAudience`, TTL ignored: 0 of 0 is not exhausted). `maybeSendExtendAudienceEmail` (`src/lib/transactional-email.ts`): `POST /send` eventType `audience_fully_contacted` (template via `PUT /platform-templates` at boot), only when sales-cold-email feature, `createdByUserId`, daily budget > 0 and org `has_auto_topup`; fail-SAFE, fire-and-forget; 1x/month/brand dedup is transactional-email's; names the brand and links its audiences page (unresolvable name = empty footer, never placeholder/id).

## Selection (what runs, per run)

- **Every run is selected**: the stored `workflow_slug` is the FALLBACK, never what runs by fiat. `dispatchSelectedRun` (`src/lib/selected-dispatch.ts`) is what `POST /campaigns` (insert AND restart), start-funded-pair's first run and `PATCH status=activate` call: `resolveSelectionForTrigger` then `executeCampaignWorkflow`. Creation is never refused because of the stored slug. `no-legacy.test.ts` pins that only `scheduler.ts`, `step-trigger.ts`, `selected-dispatch.ts` call `executeCampaignWorkflow`. Route integration tests mock the selector (macOS mDNS stalls `*.test.local` lookups, which reads as a hung PATCH).
- **Rotation is ENABLED ONLY for `sales-cold-email-outreach`** (`isWorkflowRotationEnabled`, `WORKFLOW_ROTATION_FEATURE_SLUGS`); any other feature returns `campaign.workflowSlug` with no features-service call.
- **Audience first, then workflow, from `/workflow-projection` alone** (`selectCellFromProjection`, `features-workflow-projection-client.ts`, sends `brandId` + leg params): (1) AUDIENCE by Thompson (`thompsonArgminCost`, Beta sampling, keeps exploring) over evidence POOLED across that audience's whole column (`poolArmsByAudience` sums contacted/outcomes/spend, divides spend by contacted at the END; no evidence = COLD arm, still explored); (2) WORKFLOW greedily (`greedyArgminCost`, posterior mean `(s+1)/(t+2)`, argmin(cost/rate), deterministic, ties first index) WITHIN that column on `resolved.costPerOutcomeUsd`. Do NOT revert to features-service rank #1, do NOT shuffle/rotate ties (convergence via rising floors IS the mechanism). Pooling not conditioned on a workflow is the point (a row-first pick starved cells: `lithium` $20 on 1 audience, $185-572 on 11, took 2,554 of 2,759 leads).
- **Hard constraints move with the audience pick**: `audience_ids` subset and the freshly-exhausted set (read only for a rotating feature).
- **`/start-run` CONSUMES the chosen audience** (rides the execute call; supplied = NO projection call, never re-drawn). Nothing supplied = path unchanged. It stamps `x-audience-id` on its marker run and MUST keep returning top-level `audienceId` (workflow-service threads it downstream from start-run's response). lead-service uses it without re-selecting; human-service suppression is per-brand, cross-audience. `workflowSlug == workflowDynastySlug`. Fail-soft: features-service error = configured slug, no audience, run still dispatches. Cardinality: 1 `/execute` = 1 start-run = 1 `lead-serve`; vary the workflow only on the NEXT execute. `customerProfileId`/`x-customer-profile-id` is the deprecated alias of the audience id.
- **Never reintroduce a workflow-scoped audience filter** that can collapse to a subset the stop-guard cannot see (it caused empty `lead-serve` spins; v0.44.1 deleted it). `/audience-stats` and `/features/:slug/candidates` are no longer consumed. The `/end-run` stop-guard stays UNFILTERED (sees a superset: safe).
- **The LEG's model rule is READ and binds BOTH argmins**: `readLegModelEligibility` reads `modelEligibility.eligible` ONLY (never a tier, alias or substring: `flash-pro` is cheap). `restrictToEligibleWorkflows` runs once on `rows` before either argmin, so pooled evidence and cells agree. It removes no audience (every audience is enumerated under every dynasty). Never exclude on a gap: an unreadable verdict is `null` = run UNFILTERED and WARN; a leg excluding EVERY workflow gives an EMPTY grid, `console.error`, configured-slug fallback, never widened back (the fallback slug itself is not vetted: a campaign must still run). Unvetted/no-leg campaigns read no verdict.
- **A leg campaign is priced on the leg-keyed body** (`?leg=&campaignId=&pricing=net`, same query the dashboard Workflows page ranks on, so page and pick agree). features-service 400s `leg_and_funnel` if both are sent. Funnel-keyed body is gone (C2).
- **Per-brand cohort serialization** (`serializationCohort`, `brand-turns.ts`; `hasLiveRunForBrandCohort`): asks runs-service campaign by campaign over the brand's ongoing sales-family campaigns OF ONE COHORT, never a brand-wide `listRuns({brandId})` (a PR campaign's runs would defer every sales campaign forever, invisibly). Candidate set read from the DB, not the claimed set. The three outbound cold-email channels are one cohort (same leads and mailboxes); every other channel is its own, keyed on its channel. The TURN is per cohort. Each candidate's spend is read under ITS OWN feature slug.
- **GLOBAL sales-budget mode** (`src/lib/global-sales-budget.ts` rules, `src/lib/global-sales-pot.ts` reads): billing `GET /internal/brands/:id/sales-budget` mode `campaigns` (default, byte-identical; `tests/unit/brand-turns.test.ts` is the gate) or `global`. Unreadable mode holds the brand (`budgets_unreadable`). **Owner 2026-10-03: the global budget is the ONE pot for EVERY sales campaign of the brand, reactive included** (reactive = catalogue `fromStepKey` non-null; an unnamed leg reads proactive). Pot spend = all sales-family campaigns ongoing or touched today, in-flight included; unreadable holds every candidate. Pot spent: park EVERY candidate (`global_sales_budget_reached`, info) until rollover or 10 min; a reactive lead is never dropped (its DAG claims the lead from lead-service's follow-up queue AFTER gate-check, so it stays due). Under it: reactive candidates run and take their cohort's turn first (bottom first); entry legs get only what is left: features-service `GET /offers/:id/sales-paths` flattened by ROI desc (null last, then rank), the first runnable path's (offer, `entryLegKey`, `entryChannelSlug`) campaign takes it, spilling only when no live funded campaign or at its OWN ceiling; unnamed campaigns last resort on fill ratio (logged). Binding in THREE places: planner, step trigger (skip `global_sales_budget_reached`), gate-check (`Global sales budget reached|unavailable`, fail-closed, so any dispatch path is bound). Campaign ceilings stay an upper bound. Overshoot: at most one in-flight run per cohort (cold email p95 ~$0.46, max ~$0.68; reply ~$0.06).
- **ITEMS sales-budget mode** (owner 2026-10-04 "you choose, we run"; rules `src/lib/sales-items.ts`, reads `src/lib/sales-items-pace.ts`): billing's `sales-budget` answers mode `items` (precedence items > global > campaigns) with `items[]` = one per (offer, leg, channel) the customer budgeted on an ACTIVATED sales path (`budgetCents` decimal string, `period` `day`|`month`, `periodStart/End` for month, `managed`). No global pot. Every verdict is per campaign: spent (`item_budget_reached`, `Item budget reached`), unfunded or unreadable (fail-closed) holds THAT campaign only; recheck rollover or 10 min. Planner: reactive first within a cohort. Gate-check reads the mode ONCE (`salesItemsGate` hands the read to `globalSalesPotBlock`); only single-brand campaigns can be in items mode. A brand billing never answers `items` for is byte-identical.

## Runs, scheduler, gate-check

- **Log level**: expected business states (out of credit, budget exceeded, max leads) trace at `info`, never `warn`/`error`; reserve warn/error for fail-open/closed anomalies. High-frequency routine events (per tick per campaign: dedup skips, in-flight reschedules, heartbeats) are NOT logged at all (observable in durable state). Ask "how often, across how many entities?" before logging.
- **Credit pre-filter is fail-OPEN and SAYS which happened**: `readCreditAffordability` (`src/lib/gate-check.ts`, block 3b) allows on every failure. `GateCheckResult.creditCheck` = `affordable | unaffordable | unreadable` (+ `creditCheckDetail`) rides the existing `gate-check-result` trace event (no new event/log); `unreadable` traces at `warn` (the one anomaly), `Insufficient credits` blocks with a 30-min backoff at `info`.
- **EVERY `listRuns` states a status AND a bound** (runs-service `runs` is a VIEW over 6.2M events; unbounded = whole history; was 1.76 B rows/month): stale cleanup + one-run guard read `status: "running"` with `RUNNING_RUNS_LIMIT` (200); the `completed` count enforcing `maxLeads` is a LIFETIME total asked with at most `maxLeads` rows (exact for a `>= maxLeads` comparison), read only when a cap exists; other call sites use `limit: 1`. No per-campaign run COUNT exists in runs-service; do not reconstruct one. `tests/unit/gate-check.test.ts` fails on an unbounded call.
- **A run id handed to another service MUST EXIST, never minted**: workflow-service makes `x-run-id` the `parentRunId` (FK) so a minted uuid 502s before the DAG runs and the campaign silently never runs. A campaign's `parentRunId` is its ANCESTOR run (from the creator's `x-run-id`); `ensureCampaignRunId` (`src/lib/trigger-run.ts`) is the ONE place a missing one is filled (shared by scheduler and trigger), creating a real root run persisted on the campaign BEFORE finalizing. The anchor states only life-long facts (org, user, brands, feature), completed immediately, with NO `campaignId` (campaign-scoped reads filter on it, would recreate orphans) and NO `workflowSlug` (workflow re-picked each run; a child with a different slug 409s). Fail-CLOSED: no anchor = no dispatch; `executeCampaignWorkflow` THROWS on non-2xx. `/end-run` requires `x-run-id` (`requirePipelineHeaders`).
- **Scheduler in-flight guard**: check ANY live run for the campaign via `hasLiveRunForCampaign()` (`campaignId` + `status=running` + `startedAfter=freshnessCutoff`, any service), never `(serviceName="campaign-service", taskName=campaignId)`: that marker run is an ephemeral ~2s span, while `lead-serve` (up to 755s) is a sibling under the `execute-workflow` root. `reRunDueCampaigns` and `claimStuckCampaigns` share the helper.
- **"A run is alive" is ONE definition**: `RUN_LIVENESS_THRESHOLD_MS` (`src/lib/run-liveness.ts`, 15 min, must stay above the longest flow) is imported by both the sweep and gate-check (`tests/unit/run-liveness.test.ts` fails on a literal in gate-check). `claimStuckCampaigns` FINALIZES the marker rows of an orphan it detects (marks `failed`, scoped like gate-check's read, idempotent via the claim UPDATE, fail-SOFT), emits a `campaign-recovery` event (`src/lib/recovery-event.ts`, `warn`, once per orphaned run, rides the campaign's ancestor run), catches per campaign (one bad campaign must not skip `reRunDueCampaigns`), and only touches `(ongoing, workflow_slug NOT NULL, next_run_at IS NULL)`. Residual: for 15 min after a restart an orphan looks alive; shortening needs a run heartbeat. The box restarts services on every merge.
- **Execution run tree**: `workflow / execute-workflow` (ROOT) → siblings `campaign-service / <campaignId>` (~2s marker) and `lead-service / lead-serve`. Audience attribution is FORWARD-PROPAGATED from `/start-run`'s response (`x-audience-id` is byte-equal across campaign/workflow/runs services), never root-stamped.
- **A campaign failing every run backs off and is noticed, never stopped** (#407, `src/lib/run-failure-backoff.ts`, migration 0061): `/end-run` keeps the streak on the row (`consecutive_run_failures`, `failing_since`, `last_run_failure_at`, `failure_alerted_at`). Failure on an ONGOING campaign increments (a failure > 1h after the last starts over); ANY success resets (alert latch kept). Delay: 60s for failures 1-3, then 2/4/8/16 min, ceiling 30 min. At 8 in a row (~33 min) ONE staff alert per 24h per campaign: atomic claim in the UPDATE, `POST /platform-send` eventType `campaign_failing` WITH `x-user-id` (campaign owner, else the run's user: a userless send 502s at billing authorize) (transactional-email-service owns template, staff list, per-campaign-day dedup), fire-and-forget, claim released on a failed send. Step trigger skips `failure_backoff` while a widened interval runs. Read: `GET /internal/campaigns/failing` (`runHealth.state` healthy|retrying|failing). Thresholds come from the 30-day streak histogram in the module header; never auto-stop, never email the customer.
- **Turn-planner holds say so**: every hold that parks a campaign on its own cadence emits one `campaign-hold` event (`src/lib/turn-hold-event.ts`) with `reason` (`unfunded`, `budgets_unreadable`, `daily_ceiling_reached`, `planning_failed`), the figures and `nextRunAt`, riding the campaign's ancestor run (`parent_run_id`; none = warn, never an invented one), emitted AFTER planning, fail-SOFT. The 60s TURN defer and cohort in-flight defer stay SILENT. Levels: spent ceiling / unfunded = `info`; failed read / planner throw = `warn`. Diagnose: `SELECT created_at, event, level, detail FROM run_events WHERE campaign_id='<id>' ORDER BY created_at DESC LIMIT 5;`

## History and reads other services use

- **Status history is RECORDED, never reconstructed** (migration 0057). `campaign_status_transitions` is append-only; `src/lib/campaign-status-history.ts` `setCampaignStatus` is the ONLY place a status is written (update + transition in ONE transaction; the create route writes the BIRTH in its own). `no-legacy.test.ts` fails on any `.update(campaigns)`/`.insert(campaigns)` setting `status`/`stopReason` elsewhere. `campaign_audience_availability` stores BOTH states, one row per EPISODE, written by `/end-run` only on a FLIP. `campaign_audience_exhaustion` is a PERIOD (`exhausted_at`, `last_observed_at` (TTL read), `ended_at` + `end_reason` `served`|`lapsed`; partial unique index: one open period per pair).
- **Nothing backfilled; `not_recorded` is never collapsed to `stopped`.** Migration 0057 wrote one `record_opened` row per campaign at its own timestamp (never `created_at`/`updated_at`). `earning` is `null` + `unknownReason` when either axis is unknown; responses carry `statusRecordedSince`/`audienceRecordedSince`.
- **Reads** (`requireApiKey`): `GET /internal/campaigns/:id/earning-history?from&to` and batch `POST /internal/campaigns/earning-history {campaignIds, from, to}`. A day = UTC calendar day evaluated at its END (or now); requested campaigns with nothing recorded are still returned `not_recorded`. NO money figure computed here (billing's); grain is the CAMPAIGN (never revive the brand pause table for this).
- **`GET /internal/campaigns/recurring-status?orgId=&brandId=`** (`src/lib/recurring-status.ts`), for billing's MRR: `running` = `status==='ongoing'`; `executedByPlatform` = `workflow_slug IS NOT NULL`; `kind` = `proactive` ⟺ catalogue leg has NO `fromStep` (null + `kindUnknownReason` if leg unknown; unreadable catalogue 502); `audience` = CURRENT availability period (none = `not_recorded`, `allAudiencesExhausted: null`); `recurring` = running ∧ platform ∧ proactive ∧ not exhausted, null only when it turns on an unknown. A READ, no money.
- **Mission status notification** (`lib/mission-status-notification.ts`): after a status write COMMITS, `setCampaignStatus` fire-and-forgets billing `POST /internal/brands/:brandId/mission-status-changed` (`{campaignId, featureSlug, offerId, legKey, fromStatus, toStatus}` + x-org-id/x-user-id/x-run-id/x-email; billing writes the staff email). Only a person's move (sources `patch`, `create_restart`, `start_funded_pair`, via `actor`), only when `from !== to` and not a birth; never awaited, failures swallowed. Source literals are strings because `campaign-status-history.ts` imports this module (cycle); the unit test pins them to `TRANSITION_SOURCES`.
- **Brand transfer** `POST /internal/transfer-brand` (`src/lib/brand-transfer.ts`, one transaction, idempotent): moves `campaigns` (naming the brand alone, `brand_id` or single-element `brand_ids`), `campaign_status_transitions`, `campaign_audience_availability`, `brand_pause_transitions`, and `*_snapshot_20260926` tables where they exist; brand id rewritten only on rows now under the TARGET org; co-branded campaigns stay (`coBrandedSkipped`); history not money; a target-org campaign-name collision = 409. A NEW table carrying `org_id` must be added there and to `tests/integration/transfer-brand.test.ts`.
- **`campaigns.status` is `ongoing` | `stopped`; there is NO `active`** (a `status='active'` query returns empty and falsely reads "nothing runs"). `GET /campaigns?status=` serves that vocabulary (`CampaignStatusEnum`), unrecognised = 400, never an unfiltered list; no aliasing. `limit` is optional (absent = every match), reads one row past the cap and returns `hasMore`; no cursor.
- **Frozen-history tests**: assert only the direction that stays true (what a frozen migration names is in scope), never that a growing live set is fully covered by it (`tests/unit/funnel-owner-decision.test.ts`).
